## Added after the plan: no sqlite3 on a Postgres server (DECISION-027)
- The server's Python 3.15 was built without `_sqlite3`; the API crashed on import through the Excel scratch stores.
- `SeenKeys`: mmap open-addressing hash table file (BLAKE2b-128 digest + row number), same interface.
- `_SharedStrings`: spills to `shared_strings.bin` + fixed-record `shared_strings.idx`, read through mmap.
- Removed the Postgres driver's call to the missing `_start_telemetry()` (found by the user's first Postgres start).
- With `sqlite3` blocked on import, the API and the worker load on Postgres. Excel tests: 277 passed, the same 1 order-dependent failure. 1M keys: 6.7 s (SQLite version 6.2 s), 0.4 MB traced.

## Found on the server's first Postgres starts
- A deploy ships the tracked `.env` (SQLite) and switched the server back to SQLite. Settings now also read a git-ignored `.env.local` that overrides `.env`; deploys never copy it.
- The SQLite driver gives a one-line error, pointing at `.env.local`, when Python has no `sqlite3`.
- Baseline `0001`: `mcc_master.visible_member` had `server_default=sa.text('1')`, which Postgres rejects for BOOLEAN. Now `sa.true()` (`true` on Postgres, `1` on SQLite). The offline Postgres SQL (`alembic upgrade head --sql`) has no other dialect-specific defaults.
