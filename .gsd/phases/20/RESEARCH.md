# Phase 20 Research: PostgreSQL Support

Requested by the user on 2026-11-11: use PostgreSQL in place of SQLite.

## User decisions (2026-11-11)
- PostgreSQL is the default database. SQLite stays supported through `DATABASE_URL`, so every query must run on both.
- Postgres starts empty; nothing is copied from `storage/database/realtime_transfer.db`.
- The schema is managed by Alembic migrations.
- The user installs PostgreSQL locally and gives the connection details.

## What already works
- `DatabaseConfig.driver` picks the driver from the URL scheme; `PostgreSQLDriver` exists, with a replica engine and pool options.
- Payments already uses `sqlalchemy.dialects.postgresql.insert` (`on_conflict_do_update`); the SQLite compiler renders it too.
- Every text search uses `ilike` (50 places), so search stays case-insensitive on Postgres.
- `func.date()` exists on both. The dashboard already handles text (SQLite) vs `date` (Postgres) results.
- The `server_default="1"` / `"0"` values are on Integer / SmallInteger columns, which Postgres accepts.
- Most of the ~110 "sqlite" / "strftime" hits are Python `datetime.strftime`, not SQL.
- `seen_keys.py` and `xlsx.py` used stdlib `sqlite3` for scratch files inside a job folder. Changed later (DECISION-027): the server's Python 3.15 has no `_sqlite3`, so they now use plain files.

## What has to change

| # | Finding | Fix |
|---|---------|-----|
| 1 | `asyncpg` and `alembic` are not dependencies; the exe spec bundles only `aiosqlite` | Pin `asyncpg==0.32.0`, `alembic==1.20.1`; add hidden imports and the migration scripts as data files |
| 2 | Only the SQLite driver creates tables (`create_all` + `PRAGMA` / `sqlite_master` column patches); Postgres would start with no tables | One `SchemaMigrator` runs `alembic upgrade head` at startup for both drivers |
| 3 | Both the API and the exchange worker process connect at startup, so two upgrades can race | Postgres: `pg_advisory_lock` around the upgrade. SQLite: its write lock serialises them |
| 4 | Existing SQLite databases have tables but no `alembic_version` | If tables exist and there's no version: run the old `create_all` + column patches once, then `stamp` the baseline |
| 5 | 15 columns are `DateTime(timezone=True)`. SQLite ignores the flag; Postgres would make `TIMESTAMPTZ`, read them back as UTC-aware datetimes and shift naive IST values | Make them naive `DateTime()`, matching the `now_naive_ist()` rule. No change in SQLite storage |
| 6 | The Postgres driver sets `TIME ZONE 'UTC'` and `statement_timeout=30s` with raw cursor calls on every connect | Pass `server_settings` to asyncpg: `timezone=Asia/Kolkata` (so `func.now()` defaults are IST like the app), configurable `DATABASE_STATEMENT_TIMEOUT_MS` (default 120 s) |
| 7 | Pool 20 + 50 overflow per process; the API and the worker each have one. Postgres allows 100 connections by default | Defaults 10 + 20 (60 total) |
| 8 | `conftest.py` always uses a temporary SQLite file | `TEST_DATABASE_URL` (a Postgres server URL) makes the run create a throw-away `quickyee_test_<hex>` database and drop it afterwards; without it the run stays on SQLite |
| 9 | No `.env.example`, although `scripts/init_env.py` copies it | Add one with the Postgres URL and the SQLite alternative |
| 10 | Postgres is stricter: VARCHAR length, GROUP BY, boolean vs integer, asyncpg parameter types | Found by running the whole suite on Postgres; each fix must still pass on SQLite |

## Baseline migration
Autogenerated from `Base.metadata` against an empty database, then checked by hand. Types come from the models, so the file runs on both dialects. SQLite uses `render_as_batch=True` for later ALTERs.
The `lower(email)` index stays in `ensure_indexes` (`IF NOT EXISTS` works on both).

## Risks
- Postgres can't be reached from this machine until the user installs it, so Plan 20.3 waits for that.
- The exe build (offline Windows) needs Postgres unless its `.env` points `DATABASE_URL` at SQLite. Documented in `.env.example` and the README.
